# Jina 内部重排基线

# 目标

在现有 `Infinity hybrid` 初筛之后增加一个最小内部重排步骤，专门提升候选 chunk 列表的相关性排序质量。该能力只消费已召回候选，不新增召回来源、不改变默认检索入口，也不引入新的公共 API 形态。

# 技术栈

- `Jina Reranker v3`：作为本篇唯一新增的重排能力，只在 query-time 对已有候选做相关性重排，不承担召回、去重或分数组合职责。

# 范围与非目标

本文件只定义 `Jina Reranker v3` 作为内部重排器的最小接入边界：输入是什么、输出是什么、何时允许透传以及它不负责什么。它不定义基础召回逻辑、不定义多路扩展检索编排、不定义跨路候选去重与分数组合，也不规定最终回答生成策略。V3 不在本文件扩展专用外部 API、专用配置面或专用评分链路。

# 核心契约

`Jina Reranker v3` 的输入是一次检索已经得到的候选 chunk 列表以及原始用户 query；它的输出仍然是同一批候选，只允许改变顺序并为每个候选补充 rerank 分数。该步骤只能在已有候选集合内部重排，不能补召回新的 chunk、不能丢失候选的原始标识与来源元数据，也不能把跨路候选去重或最终分数组合并入自身职责。

最小接入形态是：检索层先产出候选列表，内部重排器随后对这批候选做一次相关性排序，并将排序后的列表交给下游消费。若输入候选数量过少或重排器不可用，系统允许明确透传原始顺序，但不得隐式切换为另一套召回逻辑。无论是否触发重排，输出对象都必须保持统一候选形状，使后续编排、日志与评估链路无需为 `Jina Reranker v3` 添加专用分支。

# TDD 验收

先失败的条件是：`Jina Reranker v3` 需要专用外部 API 才能接入主链路、它在没有候选输入时自行发起召回、它把跨路去重或分数组合并入自身、或它输出了只供自己消费的专用候选结构。通过后的可观察结果是：同一批候选在进入重排前后保持标识一致；系统只在顺序和 rerank 分数上产生变化；重排关闭或不可用时可明确透传原始候选；下游无需为它增加新的公共入口或特例分支。

# 依赖与边界

本文件依赖稳定的基础召回输出契约，因为 `Jina Reranker v3` 只能处理已存在的候选列表。它可以放在单路检索之后，也可以放在多路候选完成去重与分数组合之后，但无论放置位置如何，都只对“已有候选如何重新排序”负责，不对“候选从哪里来、如何去重、如何做最终组合”负责。该能力与 ingestion 流程解耦，不承担文档入库或异步构建职责。
