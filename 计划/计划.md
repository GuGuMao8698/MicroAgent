# RAGFlow-Lite 计划

更新时间：2026-03-22

## 1. 总目标与路线

目标不是尽快做完一个玩具 demo，而是把自己推进到可以投递英飞流 `Python 实习生` 的状态。

主线只有一条：

`做一个接近 RAGFlow 的个人项目 -> 用项目暴露问题 -> 按需补知识 -> 读 RAGFlow PR -> 再反哺项目`

这条路线下，先把几件事定死：

- 不先系统学完 Python 和 Python 后端再开工。
- 不先啃数据库内核知识。
- 项目优先，PR 阅读次之，补知识放在被项目卡住的时候做。
- 先把后端主链路做通，不一开始做复杂前端。
- 不要让自己最后只剩“看了很多资料”。

## 2. 主项目定义

项目方向：

一个面向复杂文档的 RAG 系统，支持多格式文档导入、异步解析、混合检索、重排和可追溯引用。

建议项目能力范围：

- 文档上传
- 文本 / 文档解析
- chunking
- embedding
- retrieval
- 带 citation 的回答
- 逐步演进为异步 ingestion pipeline

建议技术选型：

- 后端：FastAPI
- 数据库：PostgreSQL
- 缓存 / 状态：Redis
- 检索：Infinity
- 向量化：先用现成 embedding API 或本地 embedding 服务
- 部署：docker-compose

说明：

- 初版检索选 Infinity，优先保证在 `x86-64` 环境下更便捷的本地开发体验，并从第一天固定版本。
- 先把主链路和工程能力做出来，不在初版引入计划外的复杂检索能力。

## 3. 近期先掌握的最小知识

不深学，只求能开工：

- RAG 最小链路：`document -> chunk -> embedding -> retrieval -> generation -> citation`
- chunking 基本策略
- embedding 基本概念
- BM25 是什么
- hybrid retrieval 为什么存在
- rerank 是什么
- citation 为什么重要
- PDF parsing 为什么难
- Infinity 的最基本使用
- FastAPI 最基本接口写法

当前不优先深挖很深的 `IVF` 细节、数据库恢复机制和存储引擎实现，也不在初版引入 `tensor / ColBERT / 更复杂 rerank`。眼下这条路线的主战场，仍然是把 `全文检索 + 向量检索 + hybrid retrieval + 基础 rerank / citation` 做稳。

说明：

- Python 和 Python 后端细节可以边做边学。
- RAG 的问题意识不能缺，否则项目很容易做成“上传文件 + 调 LLM”的壳。

## 4. 分阶段推进（含 PR 阅读）

PR 不要随机刷。每次读一个 PR，都固定回答这 5 个问题：

- 这个 PR 解决什么问题
- 根因是什么
- 改了哪些模块
- 为什么这样设计，而不是别的设计
- 补了什么测试，防什么回归

### 阶段一：建立最小 RAG 地图

阶段目标：

- 建立最小 RAG 心智模型
- 确定主项目技术栈
- 初始化仓库
- 跑通最小 demo

阶段产出 / 验收：

- 项目仓库初始化完成
- 可以运行最小 demo，哪怕只支持 `txt` / `md`
- 能用自己的话解释最小 RAG 主链路

同步读的 PR：

- `upload / parse / chunk / api`

### 阶段二：做出 v0 和 v1

阶段目标：

- 做出 `v0`：支持上传 `txt` / `md` / `pdf`，完成文本抽取、chunking、embedding、向量检索和回答生成
- 做出 `v1`：加入 Infinity 全文检索、hybrid retrieval、基础 citation 和基础文档元数据管理

阶段产出 / 验收：

- 可以演示完整流程：上传文档 -> 建索引 -> 提问 -> 返回回答 -> 展示引用片段
- 能解释为什么不能只做向量检索，为什么要上 hybrid retrieval
- 项目已经有一个能跑的最小 RAG 闭环

同步读的 PR：

- `search / infinity / hybrid retrieval`

### 阶段三：做出 v2，拉开和普通 demo 的差距

阶段目标：

- 加 rerank
- 让 citation 更准确，能显示 chunk 来源
- 支持基础 dataset 管理
- 支持基础 parser strategy
- 加基本日志和错误处理

parser strategy 第一版先做：

- Plain Text
- Basic PDF
- OCR fallback

阶段产出 / 验收：

- 项目具备 `hybrid retrieval + rerank + citation`
- 项目结构开始清晰，不再只是一个问答 demo
- README 开始补架构图和数据流图，已经能写进简历雏形

同步读的 PR：

- `rerank / citation / answer generation`

### 阶段四：做出 v3，体现系统工程能力

阶段目标：

- 把 ingestion 过程拆成异步 pipeline：`extract -> chunk -> embed -> index`
- 增加任务状态跟踪、失败重试、幂等处理、进度显示、基础缓存和基础性能指标

阶段产出 / 验收：

- 项目有异步 ingestion pipeline
- 有任务状态和重试机制
- 工程味明显增强，不再只是“会接 API”

同步读的 PR：

- `task executor / redis / retry / progress / async pipeline`

### 阶段五：做出 v4，开始深度贴近 RAGFlow

阶段目标：

从下面三个方向里至少选一个重点做深：

- 文档解析增强：`OCR / layout / table`
- 检索增强：`query rewrite / multi-query / eval`
- 平台增强：`dataset 管理 / parser strategy switch / ingestion pipeline 可观测性`

阶段产出 / 验收：

- 做出一个明显靠近 RAGFlow 核心能力的子系统
- 已经能有目的地读 RAGFlow PR，也能看出自己项目和 RAGFlow 的差距

同步读的 PR：

- `deepdoc / parser / OCR / layout`

### 阶段六：改进项目并尝试开源贡献

阶段目标：

- 把项目整理成可投递状态：README 重写、架构图补齐、补测试、补 benchmark 或简单评估结果、梳理关键设计权衡
- 开始尝试给 RAGFlow 做小型贡献

阶段产出 / 验收：

- 项目达到可投递级别
- 最好已经有一次小型开源贡献

优先贡献切口：

- 文档问题
- 小 bug
- 边界 case
- 测试补充
- 小的开发体验改进

### 阶段七：求职材料准备

阶段目标：

- 用项目重写简历
- 准备项目讲解版本：`30 秒 / 3 分钟 / 10 分钟`
- 准备高频问答
- 整理 GitHub 展示面
- 跟踪英飞流岗位动态

阶段产出 / 验收：

- 简历、项目、GitHub 和面试表达都准备好
- 可以正式冲英飞流 Python 实习生

## 5. 最终成果

最终至少要拿到这些结果：

- 一个公开可看的 GitHub 项目
- 一份清晰 README，讲清架构和设计权衡
- 一个能运行的 demo
- 一套最少可用的测试
- 若干高质量 issue / commit / PR 记录
- 至少一次对 RAGFlow 的小型开源贡献

## 6. 一句话结论

`用一个接近 RAGFlow 的项目，把需要的知识逼出来。`
